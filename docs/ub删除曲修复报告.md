## 1. 数据是怎么被读取的（先把机制钉死）

从游戏自己的模块里直接挖出路径模板（`strings` 抽取，非推测）：

**`modules\pkfs.dll`**（package file system）
```
/data/ifs_pack

/music/
/data/imagefs/msc/%s/%s

```

**`modules\music_db.dll`**
```

%s/%08d/%s.eve                      ← /data/music/<8位曲目ID>/xxx.eve
BNR_BIG_ID%08d / BNR_ID%08d / IDX_ID%08d
GetBnrBigName / GetBnrName / GetIdxName

⇒ 所以（与日志报错完全对得上）：

| 逻辑路径 | 实际落在磁盘 |
|---|---|
| `/data/music/90000048/idx.bin`・`bsc.eve` … | `data\ifs_pack\d9000004\90000048_msc.ifs`（**容器内部**） |

## 2. 证据链：为什么是"数据被清空"

### 2.1 症状与报错

```
W:pkfs: avs_fs_open_r() error fd=80070002, name='/data/music/90000048/bsc.eve'
W:pkfs: avs_fs_open_r() error fd=80070002, name='/data/music/90000048/idx.bin'
W:pkfs: avs_fs_open_r() error fd=80070002, name='/data/imagefs/msc/90000048/bsc.eve'
W:aep : texname error [BNR_ID90000048]
```
`80070002` = `ERROR_FILE_NOT_FOUND`；选曲后 → `SSD READ ERROR`。

### 2.2 磁盘上的文件确实"是空的"

| 文件 | 大小 | 最后写入 | 判定 |
|---|---|---|---|
| `ifs_pack\d9000004\90000048_msc.ifs` | **144** B | 2025-01-22 13:18:40 | 空壳（正常应 ~5.9 MB） |
| `d3\model\tex_l44_bnr_big_id90000048.bin` | **1** B | 2025-01-22 13:18:39 | 空壳（正常 200+ KB） |
| 同目录 `90000049_msc.ifs`（正常曲） | 6,275,824 B | 2022-08-03 | 对照 |
| `ifs_pack\d1100011\11000113_msc.ifs` | 144 B | 2025-01-22 13:18:31 | 空壳 |
| `ifs_pack\d1100100\11001007_msc.ifs` | 144 B | 2025-01-22 13:18:40 | 空壳 |

144 字节的文件是**合法的、"零条目"的 IFS 容器**（magic 仍是 `6c ad 8f 89`）——即"这首歌在这个包里没有内容"。

### 2.3 官方增量包里装的就是这些空壳（决定性证据）

用 7-Zip 直接看 `<ARCADE_DIR>\*.7z` 内部条目（`7z t` 校验 6 个包全部 OK，无 CRC 错误）：

| 增量包 | 该包内的空壳条目 |
|---|---|
| `L44JF_2024032500from2024021400` | `90000083_msc.ifs`=**144**、`tex_l44_bnr_big_id90000083.bin`=**1** |
| `L44JF_2024073000from2024060300` | `11000113_msc.ifs`=**144**；同时 `11001007_msc.ifs`=**4,964,608（真实数据）** |
| `L44JF_2024091800from2024073000` | `60000086`/`90000031`/`90000034` `_msc.ifs`=**144**，对应 `tex_*`=**1** |
| `L44JF_2024112700from2024091800` | `90000048_msc.ifs`=**144**、`11001007_msc.ifs`=**144**、`tex_l44_bnr_big_id90000048.bin`=**1** |

本机文件大小与包内条目**逐字节尺寸一致**，且写入时间 = 应用该包的时间（2025-01-22 13:18），
同一秒还写了 `music_info.xml`（1,514,963 B，与 1127 包内的**完全同尺寸**）。

⇒ **所谓"打更新包只是覆盖安装不会删数据"在这三首上不成立**：更新包把这些文件覆盖成了空壳。

### 2.4 交叉比对：坏条目恰好只有 3 首

- `data\ifs_pack` 共 1748 个 `_msc.ifs`，其中 467 个是 144 字节空壳
- `music_info.xml` 共 1108 首
- **「在列表里」且「是空壳」的 = 恰好 3 首**：`90000048`、`11000113`、`11001007`
- 另外 209 个 1 字节横幅贴图同样全部属于"不在列表里"的曲目 ⇒ 无害

> 这就解释了"部分删除曲"：**只有这 3 首是"列表里还在、数据没了"**，其余都是干脆不在列表里所以不显示。

### 2.5 一个额外的直接原因：列表本身没被同步

对比 6 个包里 `music_info.xml` 的曲目集合：

| 版本跃迁 | 曲数 | 移除的曲目 |
|---|---|---|
| 0325→0422 | 1086→1090 | — |
| 0422→0603 | →1093 | — |
| 0603→0730 | →1098 | — |
| **0730→0918** | →1100 | **60000086, 90000031, 90000034**（同时打空壳 ⇒ 干净移除） |
| 0918→1127 | →1108 | — |

即 `0918` 那次是**"删列表 + 打空壳"配套做**的；
而 `1127` 这次**只打了空壳、没删列表** ⇒ 列表里留下白图无曲名的坏条目。

### 2.6 `90000048` 与 `11001007` 是同一首歌（关键机会点）

```
music_id 90000048 : parent_id=0        name_string=83548393834c83868345  bpm=175  lv 3/6/8  is_default=1

同名、同 BPM、显式 parent 指向 ⇒ `11001007` 是 サヨナラ・ヘヴン 在 beyond ave. 的**重制版**。
而 `11001007` 的**真实数据完好地躺在 `L44JF_2024073000from2024060300.7z` 里**（它 0730 才加入、1127 才被清）。

# ★★★ 更正 + 曲目识别（2026-10-04 补充）

## `name_string` 的真相 = Shift-JIS(cp932) 假名索引
`music_info.xml` 里那个看着像乱码的 `name_string`，其实是**把曲名转成假名、再按 cp932 编码**的
「检索/排序用假名串」，并且做了归一化：**小写假名→大写、浊音/半浊音去掉**。

```
例：やっぱり雨は降るんだね -> ヤツハリアメハフルンタネ
```
验证（都能对上真实曲名）：
| music_id | name_string 解码 | 真实曲名 |
|---|---|---|
| 10000042 | ホラリス | POLARIS |
| 10000065 | エハンス | Evans |
| 10000068 | リントシテサクハナノコトク | 凛として咲く花の如く |
| 50000060 | テイリイランチスヘシヤル | Daily Lunch Special |
| 90001015 | アイシクルス | アイシクル |

⇒ 有了这个，任何 music_id 都能反查出曲名。工具：`tools\ub_song_table.py`，
产出 `ub_曲目对照表.tsv`（**1606 行**，含 id / 读音 / 难度 / BPM / 默认 / 版本 / 数据状态 / 是否在 omnimix）。

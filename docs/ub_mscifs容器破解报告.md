# `_msc.ifs` 容器破解报告

> ## 结论速览
> **`_msc.ifs` 根本没有压缩层，也没有加密层 —— 它是"裸"容器，内容全是明文。**
> 谱面就是文件尾部一段**明文 ASCII 文本**（BMS 风格），已写出可用提取器，**BPM 校验 8/8 全对**。
> 真正的压缩在**贴图**里（`PXET` → `TDXT` 纹理，KONAMI 私有 LZ），不在曲子包里。
> ⚠️ 同时**修正我上一轮的结论**：曲名**不在** `_msc.ifs` 里（既然无压缩、谱面全明文，就再无藏东西的余地）。

---

## 1. 容器结构（实测）

```
偏移        内容
0x00       魔数  6C AD 8F 89
0x04       常量  00 03 FF FC
0x08       4 B   每包不同（疑似 id 哈希）
0x0C       2 B   标志位：完整包 0x0498 / 空壳 0x0398   ← 只有两种取值
0x10       4 B   ★区段长度：完整包 0xD0(208) / 空壳 0x80(128)  ← 下一区段起点
0x14       4 B   （每包不同）
0x18      16 B   疑似 MD5/摘要
0x28      12 B   A0 42 00 FF 00 00 00 XX 01 05 BB 2B   （XX 随类型变：0x4C/0x28）
0x34      16 B   常量（空壳与完整包完全相同）
0x44 起    …     各区段
0xD0      ← 完整包在这里出现 ASCII 标记 "BMP\0"（每包都有，固定位置）→ 图片成员描述
尾部      ★谱面：明文 ASCII 文本，以 \x00 填充收尾
```

* **空壳包 = 只有前 144 B 头部**，没有任何成员（无谱面、无音频）→ 这就是官方"删曲"的形态。
* 同一首歌的两个 ID（`70001002` vs `80001002`）**只差前 0xD0 内的 40 字节**，其余逐字节相同 → 容器是确定性的、无加盐、无按文件随机的密钥。

### 1.1 熵地图证明「无压缩」

对 `70000043_msc.ifs`（5.65 MB）按 64 KB 分块测熵：

| 区域 | 熵(bits/byte) | 说明 |
|---|---|---|
| 0x000000 起 | **1.04** | 只有 `00`/`88` 两种字节（约 50%/50%）→ 纯填充/占位，**绝不可能是压缩数据** |
| 0x010000-0x320000 | 5.9 ~ 7.1 | 音频区（有损编码，熵高但**远达不到压缩数据的 7.99**） |
| 0x590000 起 | 4.90 → 3.20，可打印率 0.67 → **0.93** | ★**明文 ASCII 谱面** |
| 文件末尾 | — | `\x00` 填充对齐 |

**压缩数据必然是 ~7.99 bits/byte**；全局最高只有 7.14 ⇒ **整个容器里没有任何压缩段**，因此也没有任何"藏起来的元数据"。

## 2. 谱面格式（已完全解出）

谱面区从**第一条** `0,MEASURE ,0` 开始，到最后一个 `\r\n` 结束，行格式：

```
<时间ms>,<命令>,<参数>\r\n
```

全库 300 个包的命令统计：

| 命令 | 出现次数(300包) | 含义 |
|---|---|---|
| `PLAY` | 74,728 | 点击音符，参数 = 位置 0~15（4×4 键盘的格号） |
| `HAKU` | 34,877 | 「拍」= 节拍线（参数 0） |
| `MEASURE` | 8,918 | 「小節」= 小节线 |
| **`LONG`** | **1,063** | ★**长按/HOLD 音符**（这就是 HOLD 谱的本体！） |
| `TEMPO` | 413 | 变速，参数 = **60,000,000 / BPM**（µs per beat） |
| `END` | 1 | 结束标记 |

**`TEMPO` 参数反推 BPM 的校验（与 `music_info.xml` 对照，8/8 全中）：**

| music_id | 曲名 | TEMPO 值 | 推出 BPM | 表内 BPM |
|---|---|---|---|---|
| 70000043 | 炉心融解 | 363636 | **165.00** | 165 ✓ |
| 10000036 | bass 2 bass | 428571 | **140.00** | 140 ✓ |
| 20000016 | HOT LIMIT | 430107 | **139.50** | 139.5 ✓ |
| 10000068 | 凛として咲く花の如く | 368098 | **163.00** | 163 ✓ |
| 50000368 | 10,000,000,000 | 292682 | **205.00** | 205 ✓ |
| 20000042 | Queen's Paradise | 382165 | **157.00** | 157 ✓ |
| 10000051 | IN THE NAME OF LOVE | 387096 | **155.00** | 155 ✓ |
| 60000080 | Bad Apple!! | 434782 | **138.00** | 138 ✓ |

> 这也顺手解释了 `music_info.xml` 里 `bpm_max` 出现 **139.5 / 108.09 / 159.9** 这种小数的来源。

**提取器**：`omnisrc/ifs_extract.py` —— 给出包大小、标志位、区段长度、谱面偏移/长度、TEMPO→BPM、各命令计数，可直接用于批量扫描。

## 3. 曲名：**不在 `_msc.ifs` 里**（修正上一轮结论）

上一轮我根据"omnimix 只发 `_msc.ifs` 却不带标题字段"推测"标题随包走"。**本轮推翻**：

1. 容器**无压缩**（熵地图）⇒ 若有标题文本，一定看得见；
2. 谱面区**全明文**，命令只有 `PLAY/HAKU/MEASURE/LONG/TEMPO/END`，**没有 `TITLE` 之类**；
3. 用 120 个 ASCII 曲名、112 个 ASCII 作者名、以及 `name_string` 原始字节分别到对应包里搜 → **全 0 命中**。

所以曲名的位置仍是个悬案，但**排除范围又扩大了一圈**（连"藏在包里的压缩段"这条也断了）。

### 3.1 真正的压缩层在贴图里（新破解）

* `data/d3/model/tex_*.bin` = `PXET` 容器：`PMAN` 子表存 `(hash, 纹理序号, 名字偏移)` + 明文名字，后接纹理表 `(0, 存储长度, 绝对偏移)`。
* 纹理载荷的魔数是 **`7F 54 44 58 54` = `\x7fTDXT`**（KONAMI 的 DXT 纹理包）。
* 载荷是 **KONAMI 私有 LZ**（zlib/LZ4 都不匹配，token 形如 `.. 0F 3F .. 0F 3F`）⇒ 要出图必须逆向这层 LZ。

### 3.2 目前最像"曲名"的东西：`LCS_ID<id>`

| 事实 | 说明 |
|---|---|
| 覆盖 | **303 个曲 id**（335 条，分布在 `tex_l44*_lcs_j_*.bin`） |
| 尺寸 | ★**每首固定 8,841 字节**（4 条实测：248 / 9092 / 17936 / 26780，步长 8,844） |
| 性质 | `TDXT` 纹理（不是文本） |

**固定尺寸**是"预渲染条状图"的强特征 —— 曲绘尺寸不可能每首都一模一样，而**标题条**可以。
对照：同目录 `IDX_/BNR_` 条目尺寸是**变化**的（48,333 / 47,906 / 88,508 / 60,177 / 83,857…）= 曲绘 ✓。
⇒ 高度怀疑 `LCS`（可能是 **L**ogo **C**haracter **S**trip / **L**icensed **C**aption **S**prite）就是**曲名/标题 logo 的预渲染图**，但只覆盖 303 首。

## 4. 下一步（二选一，都能定论）

| 方案 | 做法 | 成本 |
|---|---|---|
| **A. 一句话定论** | 进游戏看选曲界面：曲名显示的是**汉字原样**还是**假名读音**（如「炉心融解」 vs「ロシンユウカイ」） | 最低。若是假名 ⇒ 谜底即 `name_string`，全案结；若是汉字 ⇒ 说明还有一层运行时/服务器来源 |
| **B. 逆向 TDXT 的 LZ** | 破掉 KONAMI 私有 LZ，把 `LCS_ID*` 渲染成 PNG 直接看是不是曲名条 | 中高，但能一次解决"真压缩层"并拿到 303 张标题图 |

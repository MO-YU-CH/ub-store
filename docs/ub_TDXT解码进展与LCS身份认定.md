# TDXT 压缩层破解进展 + `LCS_ID*` 身份认定

> 机台：`<TARGET_HOST>` jubeat beyond the Ave. (L44) / 分析对象：`contents/data/d3/model/tex_*.bin`
> 本轮结论：**`LCS_ID*` 不是"曲名条"，而是「GAME OVER 画面 / JUKEBOX 画面的 `lcs` 文本元素」**；TDXT 压缩算法仍未复现（已排除全部标准算法与 5 万+ LZSS 变体）。

## 1. PXET / TDXT 容器结构（已 100% 证实）

### 1.1 图集文件 `tex_*.bin`（PXET）

```
+0x00  'PXET'
+0x14  u32 纹理数 ntex
+0x34  u32 PMAN 名字表偏移
+0x3C  u32 纹理表偏移
纹理表： ntex × 12 字节 = (u32 flag, u32 len, u32 off)
PMAN：  [+0]'PMAN' [+4]内容长 [+16]条目数 n；条目 n × 12 = (u32 hash, u32 texIndex, u32 nameOff)
```
* 本轮实测：`ntex`/`texTableOff`/`pmanOff` 与"名字→纹理"一一对应，`LCS_ID11000023` 等名字全部从 PMAN 取得。
* **`flag` 恒为 0x00000000**（抽查 36 个、含 banner，全部为 0）→ flag 不是"是否压缩"标志。

### 1.2 每条纹理记录

```
[BE32 未压缩大小 total][BE32 压缩后大小 stored][stored 字节的负载]
```
`len（纹理表里） = 8 + stored`，实测 0 误差（例：`GMO_BLACK` len=51 = 8+43）。

### 1.3 解压后的 TDXT 头（反汇编 `afp-utils.dll` 得到，非猜测）

`afp-utils.dll` 里 TDXT 解析/字节序修复函数 **VA 0x100267F0**：

```
0x100267FF  cmp edi, 0x54584454        ; 与 'TDXT' 比较
0x1002684D  cmp esi, 0x54584454        ; 交换后比较（判断文件是大端还是小端）
...  依次 BSWAP 字段： +0x04(+4) +0x08(+4) +0x0C(+4) +0x10(u16) +0x12(u16)
                       +0x14(+4) +0x18(+4) +0x2C(+4) +0x30(u16)
0x100269BA  movzx ecx, cl              ; 格式码 = [0x14] 字段的低字节
0x100269C0  add ecx, -0x16
0x100269CB  cmp ecx, 0x20
0x100269E2  test ebx, 0xf801f          ; 合法格式码 = 0x16..0x1F 去掉 0x1B
0x100269D2  lea esi,[edx-0x40]         ; 像素区 = 头之后
0x10026A41  movzx edx, word ptr [eax+ecx*2+0x40]   ; 逐 **16bit** 取像素
```

→ **头固定 0x40 字节；像素从 +0x40 开始；像素是 16bpp；格式码 ∈ {16,17,18,19,1A,1C,1D,1E,1F}**（对应 `rgba5551rev / dxt1rev / …` 一族，字符串见 `afp-utils.dll .rdata 0x10033154`）。

### 1.4 尺寸自洽性（335/335 全中）

`(total − 0x40) / 2 % 376 == 0`，且商只取 **24** 或 **96**。这条几何约束在 335 条上 100% 成立，不可能是巧合 → `total = 0x40 + w·h·2` 且 `w = 376`。

## 2. `LCS_ID*` 到底是什么 —— 决定性证据链

### 2.1 游戏代码直接构造这个名字

`contents/jubeat.dll` 字符串表（`0x264860` 起）：

```
game_over
gmo_game_over/gmo_e_pass_use/gmo_t1000.png
gmo_game_over/gmo_author
gmo_lcs_all
LCS_ID%08d          <-- 运行时 sprintf 出的纹理名
first_play_in / normal_play_in
gmo_lcs_pos/l1-gmo_lcs   l2-  l3-  l4-  l5-
gmo_lcs_id10000000.png
```

另一处（`0x2513D8`）：`jk1-bnr_id10000000.png` … `idx_id10000000.png`、`jbx_lcs_id10000000.png`、`LCS_ID%d`。

### 2.2 aep(Flash) 资产侧的对应元素

`contents/data/aep/l44_game_over.bin` 占位表：

```
gmo_text / gmo_lcs / gmo_lcs_all / gmo_lcs_pos
l1-gmo_lcs … l5-gmo_lcs
gmo_lcs_id10000000.png
idx_mini_id10000000.png      <-- 同屏还有"迷你封面"
gmo_author                   <-- 同屏还有"作者名"
gmo_t0000..t0004 / t1000 / t1100 / t1101 / t2000 / t9000
```
`contents/data/aep/l44_jukebox.bin`：`jbx_lcs_id10000000.png`。

**⇒ `LCS_ID<music_id>` = GAME OVER 画面 `gmo_lcs` 元素贴的图；JUKEBOX 画面也用它。**

### 2.3 尺寸/版本分布（335 条 / 303 曲）

| 高度 | 条数 | 含义 |
|---|---|---|
| 376×24 | 194 | 1 行 |
| 376×96 | 141 | 4 行（4×24） |

按版本目录分组（代表）：

```
tex_l44_lcs_*     全 96      tex_l44pr_lcs_*   全 96
tex_l44ff_lcs_*   全 24      tex_l44qb_lcs_*   全 24
tex_l44cl_lcs_*   全 24      tex_l44fo_lcs_*   24 / 96 混合
tex_l44av_lcs_*   96 为主，014/016 为 24
```
**同一首曲可以在两个版本目录里各有一张（一张 96、一张 24）**，例如 `30000004`：
`tex_l44_lcs_j_03_001.bin`(96) + `tex_l44ff_lcs_j_03_001.bin`(24)。
→ 高度是**版本画布选择**，不是"内容行数"。

### 2.4 与 genre 的相关性（排除"曲名"的关键）

| genre | 有 LCS / 该类总数 | 占比 |
|---|---|---|
| toho（東方） | 58 / 58 | **100%** |
| classic | 7 / 7 | **100%** |
| UMU | 2 / 2 | **100%** |
| socialmusic | 73 / 85 | 86% |
| pops | 68 / 219 | 31% |
| anime | 24 / 115 | 21% |
| game | 7 / 43 | 16% |
| original | 22 / 891 | 2.5% |

曲名需要"预渲染成图"的曲，不会恰好是"東方/古典/UMU 全部命中、original 只有 2.5%"。
这个分布更像**「需要标原曲/作者署名的曲」**（東方=上海アリス幻樂団、classic=作曲家、socialmusic=投稿者）。
→ **`LCS` 是逐曲的文本署名条，而非曲名条。**

## 3. 压缩层：已排除 & 已观测

### 3.1 负载的固定结构

所有纹理负载（`stored` 字节）都以同一段开头：

```
7F 54 44 58 54 00 00 01 F2 F0 | <依纹理而异> | ...
   'T''D''X''T'
```
其中 `<依纹理而异>` 段里能直接读到 **未压缩大小（LE）** 与 **宽度（u16 LE）**：

| 纹理 | 负载[13..16] | = total | 负载[17..18] | 宽度 |
|---|---|---|---|---|
| LCS_ID11000023 | `40 1a 01 00` | 72256 | `78 01` | **376** |
| GMO_T9000 | `40 08 00 00` | 2112 | `40 00` | 64 |
| GMO_LCS_ID10000000 | — | 72256 | — | 376 |

即：**负载前 ~18–20 字节约等于输出头的前 20 字节**（`0x7F` 是 1 字节前缀）。`[0x14]`（格式码）位置之后才真正"被压缩"。

### 3.2 一个恒定的"斜坡"结构

所有同尺寸纹理的负载在头之后有一段**完全相同的 +18 递增序列**：

```
2d 0f 00 3f 0f 51 0f 63 0f 75 0f 87 0f 99 0f ab 0f bd 0f
00 cf 0f e1 0f f3 0f 05 1f 17 1f 29 1f 3b 1f 4d 1f
00 5f 1f 71 1f 83 1f …
```
* 按 16bit 读（含 b1 低半字节固定为 F 的重排）步长恒为 **18 (0x12)**；
* 每 8 个值插一个 `00` 字节（周期 17 字节）；
* 96 行纹理的这段公共前缀长 **405 字节**（多首曲完全一致）；起始值随纹理尺寸微移（24 行=0x0F2C、96 行=0x0F2D、T9000=0x0F2E）。
→ 说明"大片同色区域"的编码结果就是这条斜坡；**任何 LZ 都不会把常值区编成斜坡**，这是最反常的一点。

### 3.3 已排除（全部实测）

| 方法 | 结果 |
|---|---|
| zlib / raw deflate / gzip / bz2 / lzma / lzma-alone（skip 0..39 全试） | ✗ |
| LZSS flag-per-8（1=literal / 0=literal 两种极性、MSB/LSB 两种位序、12+4/11+5/10+6/13+3/9+7/8+8 各种偏移/长度切分、offset 0/1/256/4096、length 0..4 偏置） | ✗ |
| 同上但支持 3 字节 match token、flag-per-4/16 | ✗ |
| 上述 + "前 N 字节原样复制"（N = 0,8,12,16,17,…,32,64；`0x7F` 前缀 skip=0/1） | ✗ |
| 严格 oracle（`'TDXT'` + `[0xC]==total` + 宽度整除 + 合法格式码）在 rawpfx 18/19/20 全组合 13,824 种 | **0 命中** |
| 把负载直接当 8bit / 16bit 灰度、2bpp 索引 → 渲染 PNG | 纯噪声 |

### 3.4 输出规模关系（供后续参考）

| 纹理 | 输出 | 像素 | 负载 | 字节/像素 |
|---|---|---|---|---|
| LCS 96 行 | 72256 | 36096 | 9022 | 0.250 |
| LCS 24 行 | 18112 | 9024 | ~2654 | 0.294 |
| GMO_T9000 (32×32) | 2112 | 1024 | 287 | 0.280 |
| GMO_T0003 | 76864 | 38400 | 12878 | 0.335 |
| GMO_IMG_00 | 46720 | 23328 | 12751 | 0.547 |

→ 约 **2–3 bit/px**，属"轻量级图像编码"而非通用 LZ（通用 LZ 在纯色区应趋近 0）。

## 6. 下一步（三条路，按性价比排序）

### 路线 A（推荐，最省事）：机台内存取证
1. 机台上把游戏跑到 **GAME OVER 画面**（任何一首有 LCS 的曲，例如 39 / 炉心融解）或进入 **JUKEBOX** 并选中该曲；
2. 远程 `ReadProcessMemory` 扫 `jubeat.exe/spice.exe` 进程：
   `搜 "TDXT" + 该处 +0x0C 处的 LE32 == 72256`，命中即拿到**已解压的 72256 字节缓冲区**；
3. 直接按 16bpp 渲染成 PNG → 立刻看到真容，且可作为**唯一的验证基准**去反推算法。
   （拿到一张真值图，压缩算法的反推难度会断崖式下降。）

### 路线 B（纯静态，最硬）：
在 `afp-utils.dll` 里 `0x10026D20 / 0x10026E90 / 0x100267F0` 三个函数都是**虚表分发**调用的（无直接 call、无函数指针表），说明真正解码器挂在 C++ 虚接口后面。需先定位虚表初始化点（`0x100d4c78` 附近 `avs2-core` 的对象注册），再从注册处顺藤摸瓜找到 codec 实现。

### 路线 C（最直观）：截图确认语义
机台在 GAME OVER / JUKEBOX 时截图，肉眼确认 `gmo_lcs` 位置显示的是**曲名**还是**署名/歌词**，即可把 §2.4 的推断钉死成结论。

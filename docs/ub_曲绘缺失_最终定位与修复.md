# jubeat 曲绘缺失 —— 彻底定位与修复（2026-10-05 最终）

机台 `<TARGET_HOST>`，`2024112700`

---

## 1. 决定性发现：PMAN 头 `f14` 字段必须按条目数重算

PMAN 头第 6 个 u32（`f14`）是**哈希查找表的参数**，实测 9 个原版样本完全吻合公式：

```
m   = ⌊log2(n)⌋
f14 = ((2^m − 1) << 16) | 2^(m−1)        // n <= 1 时为 0
```

| n | f14 | 校验 |
|---|---|---|
| 1 | 0 | m=0 |
| 3 | 0x10001 | m=1 |
| 12 | 0x70004 | m=3 |
| 21 / 27 | 0xF0008 | m=4 |
| 36 / 51 / 57 | 0x1F0010 | m=5 |
| 147 | 0x7F0040 | m=7 |

**我此前重建图集时照抄了 base 的 `f14`**（n 变了但表参数没变）→ 游戏哈希查找表尺寸与实际条目数不符 → **所有名字都查不到** → 这正是「之前的修复都没生效」的根本原因。

### 另两处结构规则（也已修正）
- **纹理表与 `texIndex` 按「名字升序」排列**（原版 texIndex 0..n−1 与名字升序一一对应）；
- **`clen`（PMAN 内容长）需 4 字节对齐**。

修正 `omnisrc/merge_pxet.py` 后，把**原版图集读入再写出**已能与原版**逐字节一致**（仅对齐填充字节不同）。

## 2. 第二个发现：游戏的分组图集加载列表有长度上限

本次开机日志显示加载了 **55 个分组图集**，按名称字母序到 **`11_018` 就截断了** ——
`11_019`、`11_020`、`06_00x` 等**在 mod 目录里存在但从未被打开**。

用「实际加载列表」做审计，结果精确锁定：

| 贴图 | 已加载图集里查不到 |
|---|---|
| `BNR_ID` / `IDX_ID` / `IDX_MINI_ID` | **恰好 5 首：11000166 / 11000167 / 11000168 / 11000174 / 60000086** |
| `BNR_BIG_ID` | 0（在按曲打开的单曲图集里） |

**→ mod 目录里塞了 133 个分组图集，超出了加载上限，把排在后面的挤掉了。**

## 3. 本轮处置

| 步骤 | 内容 | 结果 |

| 1 | 修正 `write_pxet`：`f14` 按 n 重算 + `clen` 4 字节对齐 + 纹理表/texIndex 按名字升序 | 往返比对与原版逐字节一致 |
| 2 | **全量回滚单曲图集**为 base 原版（801 恢复 / 608 本就原版 / 210 base 占位保留复原版） | 大曲绘恢复 |
| 3 | 用修正后写入器**重建 12 个分组图集**（11 规范名 + `09_002`，含 2022 旧包 extras），并同步 rom 名 | f14 全部校验通过 |
| 4 | 把 5 首曲缺失的贴图并入**必定被加载**的小图集 `11_018`（587 KB） | **12 张已并入**；`60000086` 的 3 张本地无来源，待补 |
| 5 | 重启 | **`texname error = 0`、缓冲失败 = 0** |

## 5. 铁律（本轮血的教训）

1. **PMAN `f14` 必须按 n 重算**，绝不能沿用来源文件的值；
2. 纹理表 / `texIndex` 按**名字升序**，PMAN 条目按 **hash 升序**，`clen` **4 字节对齐**；
3. **overlay 里分组图集数量有上限**（本次观察到约 55 个被加载，按字母序截断）——
   不要盲目把所有分组图集塞进 mod 目录，否则会把需要的挤出去；
   宁可把少量贴图并入**一个确定会被加载的图集**；
4. 单曲图集 `tex_l44_bnr_big_id*.bin` 尽量保持官方原样。

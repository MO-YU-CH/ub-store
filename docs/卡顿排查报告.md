## 一、结论摘要

**未找到确切的根因来源，但定位到一个明确的异常现象，并排除了 5 个候选。**

### 已确证的事实

`mu3.exe` **长期有 2 个线程各占满一个完整物理核心**（实测 ~96% ~ 105%），
且 **`State = Running`（在跑，不是在等）**、**`CurPrio = 13`（优先级被动态提升到 13）**：

```
 TID  CPUPct  StartAddr       Module     State    CurPrio
 416   105.2  0x7FF9D6442690  ntdll.dll  Running  13
 6792  103.6  0x7FF9D6442690  ntdll.dll  Running  13
```

- 两个线程的 **起始地址完全相同** → 同一个入口函数创建的两个实例
- 进程总 CPU **稳定在 220% ~ 280%**（≈2.2~2.8 个核），而 **GPU 只有 17% ~ 28%**
- 游戏自身真正干活的线程加起来只有约 0.5 个核（主线程 24%、其余几个 1~6%）
- **⇒ 约 2 个核被持续空转烧掉，且这 2 个线程优先级高于渲染线程，会抢占其调度时间片**

**这就是"配置够但高难度卡"的合理解释**：低密度时渲染线程反正余量充足；
13 级以上音符变密，渲染线程需要更多 CPU，却被 2 个 priority-13 的自旋线程插队 → 帧时间抖动 → 掉帧。

### 但"这两个线程从哪来"——尚未定位

已逐个验证并排除下列来源（详见第二节）。**当前状态：现象确证，来源未知。**

## 九、★★★ 关键突破：`Framerate` 真正生效的正确组合

### 9.1 事实：`Framerate = 60` 在 `VSync = 1` 下**完全不生效**

用户反馈"120→60 就没那么卡了"，于是改回 60 并重启。但**实测证明这个改动没有任何作用**：

| 指标（游玩中） | `Framerate=120` | `Framerate=60` |
|---|---|---|
| GPU 利用率 | 61~79%（峰 79%） | **68~79%（峰 79%）** |
| SM 时钟 | 1916~1931 MHz | 1711~1726 MHz |
| 单核峰值 | 94% | 93% |
| 自旋线程 ×2 | ~100% / ~100% | ~100% / ~100% |

插件日志两次都是：`[FrameRate] VSync on @59 (vanilla)`

### 9.2 根因：`VSync = 1` 时插件直接忽略 `Framerate`

反查 `Assembly-CSharp.FrameRate.mm.dll`（v3.7.0，描述为 *"Fix game speed on non-60Hz display or change the frame rate"*）
的字符串，其分支只有四种：

```
[FrameRate] Framerate locked to    ← 真正应用了 Framerate
[FrameRate] Framerate unlocked     ← 无限制帧率（危险）
[FrameRate] VSync on @             ← 按 vsync 决定帧率
             (vanilla)             ← 且使用原版行为
```

> **⇒ `VSync = 1` 时，插件走 `VSync on @59 (vanilla)` 分支，`Framerate` 被完全忽略。**
> 所以「改 `Framerate`」这个动作在 `VSync = 1` 下**无论填什么数字都无效**。

（插件还引用环境变量 `MU3_MODS_CONFIG_PATH` 和 `GetEnvironmentVariable` 来定位 `mu3.ini`；
本机该变量三个作用域均未设置，但插件确实读到了文件——路径推断逻辑未完全确证，不影响上述结论。）

### 9.3 ✅ 解法（已应用并验证）

```ini
; <LOCAL_DIR>\package\mu3.ini
[Video]
Framerate = 60
VSync = 0          ; ← 关键：关掉 vsync，插件才会去应用 Framerate
```

重启后日志变为：

```
[FrameRate] Framerate locked to 60      ← ★ 插件首次真正生效
```

安全兜底核验（防止"无限制帧率"把 GPU 打满）：
```
空闲状态 GPU : 40% / 816MHz / 22.15W / 34°C   （正常，未失控）
mu3          : Session 1, PriorityClass = High
IO DLL       : ontroller-io_hid.dll, hinata.dll  （刷卡功能完好）
hinata.log   : Device connected: 7&c0220d9&0
```

**代价**：`VSync = 0` 会有画面撕裂；但对音游而言输入延迟更低，通常反而是更优选择。

**回滚**：
```
Copy-Item "<LOCAL_DIR>\package\mu3.ini.bak_vs0_<时间戳>" "<LOCAL_DIR>\package\mu3.ini" -Force   # 回到 VSync=1 + Framerate=60
Copy-Item "<LOCAL_DIR>\package\mu3.ini.bak_20260929_130401" "<LOCAL_DIR>\package\mu3.ini" -Force  # 回到原始 VSync=1 + Framerate=120
```

### 9.4 方法论教训（比结论本身更重要）

1. **判定某配置项是否生效，要去看组件自己打印的日志分支，不能只看间接指标。**
   我最初用"自旋线程数没变"判定 `Framerate` 无效——**结论对，但理由错**（自旋与帧率无关）。
2. **也不要因为用户说"有效"就放弃验证。** 用户体感与实测矛盾时，
   正确的做法是找出**能区分的硬证据**（这里就是插件日志的 `locked to` vs `vanilla` 分支 + GPU 负载对比）。
3. 对**运行中的程序**改配置，**必须重启并核对进程 StartTime 晚于配置写入时间**才算生效（见第八节事故）。

## 十、★ 全自动驱动实测：「幾望の月」MASTER 13

### 10.1 自动化是怎么做到的

**核心难点**：截图与按键注入**必须运行在 Session 1（交互会话）**，而 SSH 在 Session 0。
**方案**：在目标机放一个 Session 1 常驻代理，用**文件命令通道**通信。

```
tools/wb_agent.ps1   →  目标机 D:\wb_ctl\wb_agent.ps1（schtasks /IT 投递到 Session 1）
                         命令通道：写 cmd.txt → 代理执行 → 写 result.txt
tools/wb_ctl.py      →  Python 驱动（上传/投递/发命令/截图回传）
tools/perf_sampler.ps1 + sampler_runner.py → 高频性能采样
```
**没有用传统 OCR**：截图直接读图判读日文游戏 UI，比 OCR 可靠得多。

**踩坑**（都已解决，详见记忆）：
- PowerShell 5.1 的 `-Encoding UTF8` **会写 BOM** → 读取方要用 `utf-8-sig`
- `Register-ScheduledTask -UserId "$env:USERDOMAIN\$env:USERNAME"` 失败（`WorkGroup\administrator` 非域账号）
  → 只有 `schtasks /IT` 是可行路径
- `Start-Process` 分离启动在 SSH 会话里不生效 → 改为**用本机后台任务持有 SSH 前台阻塞运行采样器**

### 10.2 ★ ongeki 输入映射（全部实测得出）

| 输入 | 效果 |
|---|---|
| **按住 `Enter` ≈1.2s** | **模拟刷卡**（`[aime] scan=0x0D`；走 `GetAsyncKeyState` 全局读键，**不受焦点影响**；短按 80ms 无效） |
| `J`（0x4A, right1） | **決定 / 确认** |

| `A/S/D`（left1/2/3） | GP 画面无反应 |

> 🔴 **最关键结论**：**`[mu3io] path=ontroller-io_hid.dll` 存在时，键盘和鼠标完全无法驱动游戏**
> ——物理 ontroller 板独占输入。把它注释掉后，**segatools 内置 io4 键盘/鼠标映射立刻生效**，
> 上表才成立。副作用是实体控制器失效，测完必须还原。

### 10.3 实测数据（`tests/perf.log`，70s / 182 样本 / ~390ms 一采样）

| **GPU 利用率** | 平均 **72.5%**，最大 **80%**，**≥95% 的样本 0 个**，≥85% 也 0 个 |

### 10.4 结论

**CPU 和 GPU 都没有被打满** —— 这个谱面在 `VSync=0 + Framerate=60` 下**不是吞吐量瓶颈**。

两个可量化的改善迹象：
1. 按 `利用率 × 时钟` 粗算，GPU 实际工作量比 VSync=1 时**下降约 23%**（69%×1916 → 79%×1284）
2. 帧输出**更平稳**：利用率曲线从 `61~79%` 波动变成**恒定 79%**（说明帧时间更均匀）

**客观指标全部正常，最终体感需要你试玩判定。**

## 附录 C　排查方法说明与坑

1. **SSH 会话与游戏不在同一 Windows 会话**：SSH 在 `Session 0(services)`，游戏在 `Session 1(console)`。
   - 直接在 SSH 里启动游戏会跑在无桌面的 Session 0，观测失真
   - **正确做法**：用 `schtasks /create /tr "start.bat" /sc once /st 23:59 /it /f` + `/run` 投递到交互式会话
   - 已核实：**删除该计划任务不会杀掉已启动的游戏**（`mu3 仍在运行`）
2. **SSH 会话里查分辨率/前台窗口全是假的**：`[System.Windows.Forms.Screen]` 得到 `WinDisc 1024x768`、
   `GetForegroundWindow` 得到 `Idle`(pid 0) —— 都属服务会话。涉及显示状态的结论以
   `Win32_VideoController` 与**游戏自身 Unity 日志**为准。
3. **`Get-Process` 的 `CPU` 是累计秒数，不是百分比** → 必须**双采样差分**；
   线程级同理用 `ProcessThread.TotalProcessorTime` 双采样，这是本次抓到忙等线程的关键手段。
4. **Windows OpenSSH 7.7 会吞掉命令里的双引号**（实测 `Write-Output "a b"` 输出两行）
   → 所有远端命令走 **UTF-16LE + Base64 的 `-EncodedCommand`**。
5. **PowerShell `-replace "(?m)^...$"` 对 CRLF 会静默失配**（`$` 匹配在 `\n` 前，`[ \t]*` 吃不掉 `\r`）
   → 改远端配置文件用 **SFTP 拉下来做 Python 字节级 `re.subn` → 回传 → 再拉一次逐字节校验**。
6. **A/B 实验必须验证"改动真的生效了"**，否则会得出错误结论。
   本次实验 4 就是靠 `hinata.log` 的 mtime 没变 + 模块列表里没有 `hinata.dll` 才确认有效的。

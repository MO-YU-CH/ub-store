**结论：这两条不是「被漏掉的曲子」，而是同一份谱面数据的旧 ID 副本 —— 它们对应的曲目早就在表里了。**
把它们加进曲目表只会产生**重复曲目**。已回退。

## 1. 原先的判断（错的）

上一轮的依据是「覆盖层有完整数据、基线只有 144 B 空壳」：

| music_id | 覆盖层 `_msc.ifs` | 基线 `_msc.ifs` | 当时的结论 |
|---|---|---|---|
| `70001002` | 5,834,656 B | 144 B | 疑似被删曲，可补 |
| `70001005` | 5,925,840 B | 144 B | 疑似被删曲，可补 |

再叠加「包尺寸接近」的近似匹配，把母曲猜成了：

* `70001002` → `50000031`（当时认为是 quaver♪ / Risk Junk）
* `70001005` → `50000166`（当时认为是 LANA - セカイノハズレ -）

**这两条母曲判断都是错的。** 5.8 MB 的压缩包出现几十 KB 的尺寸巧合很常见，尺寸根本不是可靠的指纹。

## 2. 决定性证据：逐字节差分

把覆盖层文件与基线文件直接按字节比对：

| 对比 | 文件大小 | **不同的字节数** | 差异位置 |
|---|---|---|---|
| `70001002_msc.ifs` vs `80001002_msc.ifs` | 5,834,656 / 5,834,656 | **40 B** | 全部落在前 `0xD0` 字节内（7 段） |
| `70001005_msc.ifs` vs `80001001_msc.ifs` | 5,925,840 / 5,925,840 | **40 B** | 同上 |

差异只在 IFS 头部的 4 字节文件标识 / 虚地址字段（例如 `0x08` 处 `57bffacf` vs `594b8691`），**正文 5,834,616 字节完全相同**。两个不同的曲子不可能有逐字节相同的音频+谱面，所以这只能是同一份数据的两个 ID 副本。

以 2048 B 为块做集合重叠（A∩B/|A|）：

| 组合 | 重叠率 |
|---|---|
| 已知 HOLD/母曲对（`80001001`↔`70000043`） | 98.768 % |
| 已知 HOLD/母曲对（`80001011`↔`70000047`） | 98.853 % |

| 已知 HOLD/母曲对（`90001003`↔`50000148`） | 98.813 % |
| **`70001002` ↔ `80001002`** | **99.965 %** |

| `70001005` ↔ `50000166`（原猜测的母曲） | 0.035 % |

原本猜测的两首母曲重叠率为 **0**，彻底否定。

## 3. 它们的真实归属

| 旧 ID | 等价于 | 母曲 | 母曲读音 | HOLD 谱等级 |
|---|---|---|---|---|
| `70001002` | `80001002` | `50000204` | イコウセロカタ | **3 / 7 / 9**（detail 3/7/9.8） |
| `70001005` | `80001001` | `70000043` | ロシンユウカイ（= 炉心融解） | **2 / 6 / 8**（detail 2/6/8） |

* `80001001` / `80001002` 的声明字段里本来就写着 `is_hold=1`、`parent_id=70000043 / 50000204`，是**它们各自的 HOLD 谱**。
* 曲绘也印证：`80001001` 与 `70000043` 的 `tex_l44_bnr_big_id*.bin` 大小相同（329,648 B），纹理表 `(0, 0x50727, 0x88)` 完全一致 → HOLD 谱与母曲**共用同一张曲绘**（与「39 / 39[2] 共用曲绘」是同一机制）。
* 上一轮为这两条借用的等级（来自 `50000031` / `50000166`）**本来就是错的**；正确等级一直在 `80001002` / `80001001` 里。

## 4. 为什么会存在这种「旧 ID 副本」

jubeat 的 HOLD 谱按版本分块编号：`60001xxx`(prop) → `70001xxx`(Qubell) → `80001xxx`(clan) → `90001xxx`(festo) → `11001xxx`(beyond the Ave.)。

`70001xxx` 块在 and 基线表里只剩 `001 / 004 / 007` 三条，`002 / 003 / 005 / 006` 已被官方更新删除。**omnimix 数据包是拿更早的整包数据做的**，所以把 `002`、`005` 的数据一起打了进去 —— 但曲目表（`music_omni.xml`）里并没有它们，于是变成了「有数据、无引用」的孤儿包。

它们被删的原因就是被后来 clan 期的 `80001xxx` 重新发行取代了（数据一模一样）。

## 6. 教训（写进流程）

1. **MB 级压缩包的尺寸巧合很多**，别拿尺寸当指纹；`_msc.ifs` 的**块级重叠率**才是可靠的近重复判据（母曲对 ≈ 98.8 %，同一份数据 ≈ 99.96 %，无关曲 ≈ 0 %）。
2. 「基线空壳 + 覆盖层有数据」**不等于**「这是一首被漏掉的新曲子」—— 也可能是同一份数据的旧 ID 副本。**必须先做去重判定再往表里加**。
3. 这一点同样适用于另外 128 个孤儿包：它们多半都是这种「旧 ID / 无引用」残留，**不代表缺失曲目**。
